● Yes — entirely possible, and a natural feature given each env is its own
  ostree stateroot in a separate subdir of TBOX_STORE.

  Design in 3 sentences:

  1. From any booted env, the other envs' ostree repos are reachable on disk
   at <store>/tbox-install/<env>/ostree/repo. ostree CLI happily operates on
   a non-booted repo with --repo=<path>.
  2. A tacklebox update-all command would: read the original recipe (write
  it to TBOX_PERSIST/recipe.json at build time so it's discoverable
  post-install), then for each <env> other than the booted one: bootc switch
   --apply --no-finalize <recipe.image> against that stateroot's repo
  (stages a deployment but doesn't reboot).
  3. Next time the user boots into that env, bootc finalizes the staged
  deployment automatically; if there's a bug it greenboot-rolls-back, same
  as a normal upgrade.

  The catch: bootc's CLI prefers operating on the booted sysroot. For
  non-booted, you have to work in ostree primitives:
  - ostree pull --repo=<other>/ostree/repo <remote> <ref>
  - ostree admin deploy --repo=<other>/ostree/repo --sysroot=<other> <ref>

  That's ~30 lines of Go orchestration plus persistence of the recipe at
